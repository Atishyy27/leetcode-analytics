## What it is, and who uses it

A Chrome extension that puts community problem ratings (zerotrac dataset) on the LeetCode profile, problem page and problem list. The user is a LeetCode practicer who wants to know where they stand by rating, not by Easy/Medium/Hard.

## First-run path, walked from the code

1. Install. Nothing happens by itself. Clicking the toolbar icon opens the options page (background.js:313), which holds switches and a cache button and no "what do I do now". A LeetCode tab that was already open has no content script until refreshed (standard Chrome behaviour, not verified live).
2. Open a problem page. The chip shows rating, slot, contest. The "above/below your level" part needs `level`, which is only written when the profile panel has run (profile.js:417-419) and expires after 12 hours (UNIVERSE_TTL). Reader: problem.js:82-88. So a new user never sees it before visiting their profile, and an existing one loses it 12 hours after the last profile visit.
3. Open the profile (signed in). First sync reads the whole list: 4124 problems / 100 = 42 POSTs, 3 at a time (gql.js:185-216), with a progress bar. After that, nothing for 12 hours (profile.js:15).
4. Solve a problem, come back. Counts do not change for up to 12 hours (universe cache); recent solves for up to 30 minutes (RECENT_TTL). The only way out is the "Re-sync now" button on the Data tab (profile.js:332), the last tab.
5. Rating table: the bundled snapshot is 15 Oct 2026; the weekly live refresh is off (store.js DEFAULTS liveRatings false) and needs a permission prompt on the options page.

## Findings, ranked

1. Own new solves do not show up for up to 12 hours (profile.js:15, :402).
2. The rating table was five weeks old at publish time and ages every week; new contest problems show "no contest rating" (problem.js:93-95) and are left out of the counts. Fresh data is possible but off and hidden.
3. A failed or signed-out identity lookup shows "This is not your profile" on your own profile (profile.js:357, :390-399), hides your coverage and gives no way to fix it.
4. The chip loses "above/below your level" 12 h after the last profile visit and never has it on a fresh install (problem.js:84, profile.js:418).
5. Install gives no direction: icon click opens options (background.js:313).
6. Re-sync lives on the last tab (profile.js:332).
7. Surfaces rely on guessed DOM anchors (profile.js:28-64, problem.js:45-60) with a fallback to the end of the page body; no test, live DOM not checked.
8. fetchProfile is dead code (gql.js:253, no caller in src); README says about 3,700 problems, live is 4124.
Items 4 to 8 are not in the top 3; they go to "extra ideas".

## Top 3 changes

### 1. Your newest solves count immediately

What you notice: solve a problem, open your profile, and the count and coverage move that minute instead of tomorrow.
Evidence: profile.js:15 (12 h cache); profile.js:392 already fetches your 20 latest accepted solves, whose slugs are exactly what the cache lacks.
Plan: on your own profile, always fetch the 20 latest accepted (one request) and mark those slugs solved in the cached problem list, then store it back. No 42-request resync. Beyond 20 new solves since the last sync, the 12 h rule and the Re-sync button still apply and the panel says how old the full list is, as today.
Expected effect: after solving k <= 20 problems, solved counts are right within one profile view (today: wrong for up to 12 h). Cost: one request per profile view.
Proof: unit tests with mocked GraphQL and a fake store: a cached list with 3 unsolved, recent list holding 2 of them plus 1 already solved: ratedSolved goes up by 2, the already solved one changes nothing, request count is 1, a 25-solve gap leaves the staleness note in place. A product test of the profile flow against the mocks.
Risk: a recent slug the list does not know (renamed or contest-only) is ignored, never invented, so no worse than today. One extra request per profile view.

### 2. Ratings that are not five weeks old

What you notice: problems from the latest contests have ratings, and the panel says plainly when its ratings are old and how to keep them fresh.
Evidence: snapshot 15 Oct vs upstream 21 Nov: 36 problems missing (1.4% of 2644), six contests behind on weekly (522 vs 528) and three on biweekly (192 vs 195); weekly upstream cadence; live refresh off by default.
Plan: (a) refresh data/ratings.tsv with the existing tools/build-data.cjs, one data-only commit; (b) when the snapshot is older than 21 days, show one line on the Overview note and the chip tooltip: "Ratings are N days old. Turn on weekly refresh in options"; the optional permission and options switch already exist, no manifest change; (c) export convertUpstream from background.js so it can be tested.
Expected effect: problems missing against upstream 36 -> 0 on the refreshed snapshot; a stale line appears at 22 days. It reaches users only when you upload a new store version; that and any version bump stay your call.
Proof: tests on convertUpstream with a synthetic upstream fixture (good file, renamed column, under 1000 rows); the 21-day rule with a fixed clock; build-data row count equals upstream's unique slugs; node tools/check.cjs.
Risk: 8 existing ratings move (largest 187), so a few users' numbers shift slightly. Any new host permission would disable the extension for all 224 users until accepted (Chrome permission-warnings doc), so this plan adds none.

### 3. Say what is wrong instead of "not your profile"

What you notice: signed out, or a failed lookup on your own profile, now says "Sign in to LeetCode to see your coverage" or "Could not reach LeetCode" with a Retry button, instead of a wrong claim.
Evidence: gql.js:166-175 returns null for both signed-out and any error; profile.js:390-399 and :357 turn null into "This is not your profile".
Plan: whoAmI returns one of: a username, signed-out, or error. The profile surface shows a message and a retry for each; the genuine other-person view is unchanged.
Expected effect: two currently wrong screens become correct and recoverable; no change on the signed-in happy path.
Proof: mocked GraphQL returning signed-out, 429 persisting past the retries, 500, a timeout and a slow response; assert the message, and that Retry re-runs once per click. 360 px layout of the message checked in CI (Playwright, never local).
Risk: low. Message copy is the only visible change; retry must not loop.

## References (free, public)

1. zerotrac/leetcode_problem_rating README: ratings estimated by Elo and maximum likelihood, "updated every week after the contest(s)", contests 1 to 62 excluded. We take: upstream is weekly, so a bundled file is stale by design.
2. Chrome docs, permission warnings: an update that adds a warning-triggering permission disables the extension until the user accepts; runtime permissions are recommended. We take: keep the refresh optional and add no host permission.
3. Chrome docs, permissions API: permissions.request must come from a user gesture. We take: the stale line points to the options switch, never a silent request.
4. The LeetCode GraphQL endpoint itself, probed unauthenticated on 25 Nov 2026: all five queries answer. We take: the field contract the mocks must copy, and a re-probe before each release.
5. zerotrac README lists "LeetCodeRating" and "refined-leetcode" as related Chrome extensions (for LeetCode-China). Listed only; not opened. We take nothing yet.
